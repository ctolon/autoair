# i18n (English and Turkish)

Procedure: skill `i18n-strings`.

- Instance: `frontend/src/i18n/index.ts` (`fallbackLng: "en"`; language from localStorage
  `autoair.lang`, then Airflow's `i18nextLng`, then the browser). Namespaces are one JSON file
  per language, `locales/{en,tr}/<namespace>.json`, loaded by a glob; a new namespace is also
  listed in `FEATURE_NAMESPACES`.
- Every key exists in both languages at the same path, with the same `{{vars}}`; plurals use
  i18next suffixes (`_one`, `_other`); never build sentences from translated fragments.
- Server texts reach the UI as a stable code plus params next to the English text: problems via
  `problemText(p)` (`lifecycle:problemText.<key>`), troubleshoot results
  `ai:troubleshoot.result.<code>`, KB source reasons `admin:kb.reason.<code>`. Unknown codes
  fall back to the English message.
- Turkish uses proper characters (ı, ş, ğ, ü, ö, ç, İ) and sentence case like the English. When
  unsure of a translation, keep the meaning exact and flag it rather than guess. Turkish strings
  are often longer: nothing may overflow or truncate without a tooltip.
- Check: `cd frontend && npx vitest run src/i18n/parity.test.ts` (every namespace: same keys,
  same `{{vars}}`, no empty `tr`).
