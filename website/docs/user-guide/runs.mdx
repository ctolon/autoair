title: Runs
description: Trigger, backfill, clear and pause DAGs from the builder, follow a run on the canvas, read task logs and XComs, and test tasks in a sandbox.
---

Once a DAG is deployed and parsed by Airflow, you can operate it from the builder. You can trigger and backfill runs, pause and unpause the DAG, clear a run, watch task states on the canvas, and read logs and XComs. Every one of these calls goes to Airflow's REST API **with your own credentials**, so Airflow's RBAC applies on top of AutoAir's permissions. Before deploying, you can also **test** a task or the whole DAG in a sandbox on the AutoAir server, without involving Airflow.

## Requirements

| Feature | Flag | Permission |
|---|---|---|
| Runs list, overlay, logs, XComs, DAG status | `features.airflow` | `airflow:read` |
| Trigger, asset test events | `features.runs` + `features.airflow` | `run:trigger` |
| Pause/unpause, scheduling state, clear, backfill | `features.runs` + `features.airflow` | `run:manage` |
| Asset materialize | `features.runs` + `features.airflow` | `run:trigger` |
| Test a task or DAG | `features.test_runs` | `run:test` |

All flags default to `true` (`AUTOAIR_FEATURES__RUNS`, `AUTOAIR_FEATURES__TEST_RUNS`, `AUTOAIR_FEATURES__AIRFLOW`). In `autoair local` there is no Airflow, so runs and test runs are off. When a feature is off, its menu items and tabs are hidden and its API routes answer 404. Built-in roles: **Operator** has `run:trigger` and `run:manage`, **Deployer** has `run:trigger`, and **Author** has `run:test`. The default `Authenticated` baseline also includes `run:trigger` and `run:manage`, which leaves the decision to Airflow. See [IAM](/docs/admin/iam).

Trigger and backfill need the DAG in Airflow. Until it is there, they are disabled with "Deploy the DAG first: this needs it in Airflow." A missing permission shows "You don't have permission for this (&lt;permission&gt;). Ask an AutoAir admin."

| Place | Contents |
|---|---|

| **Runs** tab (bottom panel) | Recent runs, with **Trigger…**, **Backfill…**, **Clear run…**, **Clear overlay**, **Analyze with AI** and refresh |
| **Task** tab | Logs and XComs of the selected task in the selected run |
| **Airflow** tab | Parse status, import errors, latest runs, DAG bundles, **Trigger…**, the **Scheduling** selector (Airflow 3.4+) and the **Trigger endpoint** snippets |

## Trigger a run

1. Choose **Run → Trigger…**, or **Trigger…** in the Runs or Airflow tab.
2. In **Trigger DAG run** ("Start a run of &lt;dag_id&gt; in Airflow."), fill in:

   | Field | Description |
   |---|---|
   | **Run configuration** | A form generated from the DAG's [params](/docs/user-guide/params-and-trigger-forms), prefilled with their defaults. If an [environment](/docs/user-guide/environments) is selected, its param overrides are prefilled too. **Edit as JSON** switches to raw JSON. A DAG without params shows a plain **conf (JSON)** editor: "Run configuration (dag_run.conf). Keys matching DAG params override their defaults." |
   | **Logical date** | **Now** (the trigger time), **Specific date** (interpreted in your local time zone) or **None** (no logical date, for Airflow 3 asset- or partition-style runs) |
   | **Partition key** | Optional, for partitioned DAGs |
   | **Note** | Stored on the run in Airflow |
   | **Unpause the DAG if paused** | On by default. A paused DAG's runs would otherwise not start. |

3. Click **Trigger**. On "DAG run triggered", the new run is selected in the Runs tab and its overlay appears on the canvas. On failure, the toast **Trigger failed** carries Airflow's error message.

## Follow a run on the canvas

The **Runs** tab lists the 50 most recent runs and refreshes every 10 s. The columns are **Run**, **State**, **Type**, **Logical date**, **Started**, **Duration** and **Bundle version**. For git bundles, the bundle version is the commit the run is pinned to. Click a row, or press Enter or Space on it, to show that run on the canvas. Click it again to deselect.

While a run is shown:

- Each task's border and background take its state colour. When the task has more than one try, the task chip adds the try number (`#2` for the second try), and `[n]` for a mapped task.
- Mapped tasks show one combined state, the worst one first: failed, upstream failed, up for retry, restarting, running, awaiting input, deferred, up for reschedule, queued, scheduled.
- A legend panel shows the run ("&lt;type&gt; run · &lt;when&gt;") with **Show the state legend** / **Hide the state legend**, and a **Hide run overlay** button. **Clear overlay** in the Runs tab does the same.
- While the run is active, the overlay is polled every 3 s. A run counts as active when its state is running or queued, or when any task is running, queued, scheduled, deferred, up for retry, up for reschedule, restarting or awaiting input.
- A blue dot on the **Runs** tab title shows that an overlay is active.

## Task logs and XComs

<Screenshot name="task-logs" alt="The Task tab showing a task's log with a search field, a try selector, a Follow toggle and an XCom sub-tab" caption="Task tab: logs per try, search and follow." />

1. Select a run in the **Runs** tab ("Select a run in the Runs tab.").
2. Click a task on the canvas ("Select a task on the canvas to see its logs and XComs.").
3. The **Task** tab shows:
   - A **Try** selector, from 1 to the latest try. It defaults to the latest.
   - A **Map index** selector for mapped tasks.
   - **Logs**: the full log of that try. **Search the log…** filters matching lines and shows the count ("N matching lines"). **Follow** keeps the view scrolled to the end.
   - **XCom**: the values the task pushed ("No XCom values." if none).

Logs are fetched in full and refreshed every 3 s (XComs every 5 s) while the task is still active and the run is active. They are not streamed. A task that has not started yet shows "&lt;task&gt; hasn't started in this run yet" and "Logs and XComs appear here once the scheduler starts it."

When AI is available (`ai:use`), **Analyze with AI** in the Runs and Task tabs opens the [troubleshooting assistant](/docs/ai/troubleshooting) on the selected run or task instance.

## Clear a run

Select a run and click **Clear run…**. **Clear DAG run** re-queues task instances of that run ("Cleared task instances are scheduled again.").

| Option | Default | Shown when | Effect |
|---|---|---|---|
| **Only failed tasks** | on | always | Clear only the failed tasks. Turn it off to clear every task of the run. |
| **Only new tasks** | off | Airflow 3.2+ | Queue only the tasks added in the latest DAG version. Turning it on turns off **Only failed tasks** and **Keep task state**. |
| **Keep task state** | off | Airflow 3.4+ | Keep the tasks' state store so the next attempt resumes where it stopped. AutoAir then calls Airflow's `clearTaskInstances` endpoint for the run instead of the DAG run `clear` endpoint. Cannot be combined with **Only new tasks**. |
| **DAG version** | **Default (DAG / Airflow setting)** | Airflow 3.1+ | Which bundle version the re-run uses: **Default (DAG / Airflow setting)**, **Latest version** or **The run's original version** (`run_on_latest_version` null, true or false). |

1. Choose the options.
2. Click **Preview** for a dry run listing the affected task instances (task id, map index, state). Changing an option discards the preview.
3. Click **Clear**. The toast reads "Run &lt;run_id&gt; cleared" or "Clear failed" with Airflow's message.

## Backfill

**Run → Backfill…** or **Backfill…** in the Runs tab ("Create runs of &lt;dag_id&gt; for a past date range."):

| Field | Default | Description |
|---|---|---|
| **From** / **To** | the last 7 days | The end must be after the start. |
| **Reprocess existing runs** | **None (only missing runs)** | Or **Failed runs**, or **All completed runs**. |
| **Max active runs** | `10` | Concurrent backfill runs. |
| **Run backwards (newest first)** | off | |
| **DAG version** | **Default (DAG / Airflow setting)** | Airflow 3.1+ only. Which bundle version each backfilled run uses, as in **Clear DAG run**. |
| **Drain the DAG** | off | Airflow 3.4+ only. No new scheduled runs during the backfill; the DAG pauses once its unfinished runs finish. Ignored by the dry run. |
| **conf (JSON, optional)** | | Passed to every backfilled run as `dag_run.conf`. Must be a JSON object. |

Click **Dry run** first. It lists the "Runs that would be created". **Create backfill** stays disabled until a dry run has been done ("Preview the runs with a dry run first"). The toast reads "Backfill created" or "Backfill failed".

## Pause and unpause

The toolbar chip shows **paused** or **active** once Airflow has parsed the DAG, and **not in Airflow yet** before that. Click it to toggle (`run:manage`). Unpausing asks for confirmation: "The scheduler will start creating runs for it (and catch up missed intervals if catchup is on)."

### Scheduling state (Airflow 3.4+)

Airflow 3.4 replaces the paused flag with a three-way scheduling state. When the connected Airflow supports it, the **Airflow** tab of the bottom panel shows a **Scheduling** selector next to **Trigger** for a parsed DAG:

| State | Meaning |
|---|---|
| **active** | The scheduler creates runs as usual. |
| **draining** | No new scheduled runs are created; runs already started finish, and the DAG pauses once its unfinished runs finish. The tab also shows an orange **draining** badge. |
| **paused** | No runs are scheduled. |

Changing it calls `PUT /api/airflow/dags/{dag_id}/scheduling-state` and needs `run:manage` and `features.runs`; the selector is disabled without the permission. The toast reads "Scheduling state changed" or "Changing the scheduling state failed". The selector is hidden on Airflow versions before 3.4.

## Airflow version capabilities

Options that only newer Airflow versions accept are shown only when the connected Airflow has them, because Airflow's request bodies are strict: an unknown field fails the whole call. AutoAir reads the server's version from Airflow's `GET /api/v2/version` through `GET /api/airflow/capabilities` (cached for five minutes in the browser). If the Airflow server cannot be asked, it falls back to the version of the Airflow installed next to AutoAir (`"source": "installed"`); if neither is known, every optional feature is off (`"source": "unknown"`).

| Capability | Airflow | Where in the UI | API |
|---|---|---|---|
| `materialize` | 3.0+ | **Materialize** on a registered asset ([Asset events](/docs/user-guide/scheduling-and-assets#asset-events)) | `POST /api/airflow/assets/{asset_id}/materialize` |
| `clear_run_on_latest_version` | 3.1+ | **Clear DAG run → DAG version** | `run_on_latest_version` on `POST /api/airflow/dags/{dag_id}/runs/{run_id}/clear` |
| `clear_only_new` | 3.2+ | **Clear DAG run → Only new tasks** | `only_new` (not with `only_failed` or `keep_task_state`) |
| `keep_task_state` | 3.4+ | **Clear DAG run → Keep task state** | `keep_task_state` |
| `backfill_run_on_latest_version` | 3.1+ | **Backfill → DAG version** | `run_on_latest_version` on `POST /api/airflow/dags/{dag_id}/backfill` |
| `scheduling_state` | 3.4+ | **Scheduling** selector; **Backfill → Drain the DAG** | `PUT /api/airflow/dags/{dag_id}/scheduling-state`; `drain_dag` on the backfill |

```json title="GET /api/airflow/capabilities"
{
  "version": "3.4.0",
  "source": "server",
  "materialize": true,
  "clear_run_on_latest_version": true,
  "clear_only_new": true,
  "keep_task_state": true,
  "backfill_run_on_latest_version": true,
  "scheduling_state": true
}
```

Operations that Airflow's own UI offers per task, such as marking a task success or failed, clearing a single task, or deleting a run, are not available in AutoAir. Use the Airflow UI for them.

## Trigger snippets

To trigger the DAG from a script, CI job or webhook, use the **Trigger endpoint** card in the **Airflow** tab: it shows Airflow's `POST /api/v2/dags/<dag_id>/dagRuns` endpoint with copyable **curl**, **Python requests**, **JS fetch** and **Airflow CLI** snippets, the `conf` prefilled from the param defaults. See [Trigger snippets](/docs/user-guide/params-and-trigger-forms#trigger-snippets). AutoAir's own `POST /api/airflow/dags/{dag_id}/trigger` (`{"conf": {...}, "logical_date": "now", "unpause": true}`) is an alternative when the caller authenticates against AutoAir instead of Airflow.

## Test a task or the DAG before deploying

**Run → Test selected task…** or **Test whole DAG…** runs the current, possibly unsaved, document in a sandbox on the AutoAir server. Nothing is written to Airflow, and no deploy is needed.

- **Single task**: choose the **Task**. Under **Upstream XCom values**, provide mock values for the XComs it reads. They are prefilled from the run shown in the overlay ("prefilled from run …"). **Mock another upstream task…** adds more. Click **Run task**.
- **Whole DAG**: choose the **Mode**. **In memory (no metadata DB)** runs without Airflow's database. **dag.test() (writes a run)** uses Airflow's `dag.test()`. **Auto** tries `dag.test()` and falls back to in-memory. Click **Run DAG**.
- **conf / params (JSON)** is prefilled with the param defaults.

Results show the state, duration, return value, XCom pushes, skipped downstream tasks and the captured log. For a whole DAG, the results are a table with one row per task. The possible states are `success`, `failed`, `skipped`, `upstream_failed`, `deferred`, `timeout`, `import_error`, `not_found` and `error`.

The sandbox is a fresh interpreter in its own process group and temporary directory. Its environment has AutoAir's secrets removed, and the whole process group is killed at the timeout. A mapped task runs only `map_index=0`. Because a test executes DAG code on the AutoAir server, it needs `run:test`, and Python tasks need `allow_python_code`.

| Setting | Default | Description |
|---|---|---|
| `AUTOAIR_RUNNER__DEFAULT_TASK_TIMEOUT` | `120` | Seconds per task test |
| `AUTOAIR_RUNNER__DEFAULT_DAG_TIMEOUT` | `300` | Seconds per DAG test |
| `AUTOAIR_RUNNER__MAX_TIMEOUT` | `600` | Largest timeout a request may ask for |
| `AUTOAIR_RUNNER__MAX_LOG_CHARS` | `64000` | Captured log size |
| `AUTOAIR_RUNNER__MAX_VALUE_CHARS` | `4000` | Size of each returned value shown |

Test runs are rate-limited per user (`limits.rate_limits`, group `test_runs`). See the [configuration reference](/docs/reference/configuration#runner).
